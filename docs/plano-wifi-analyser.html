Plano inicial — Wi‑Fi Analyser

Projeto: Mestre-do-PC-V10 · Data: 2026-10-31 · Status: rascunho editável

Como editar: clique em qualquer bloco cinza e digite. Use Salvar no navegador para guardar no localStorage desta máquina. Use Baixar HTML para levar o arquivo atualizado.

1. Objetivo

Transformar a análise Wi‑Fi do Mestre (hoje um relatório via rede_wifi_analise + painel Rede) num Wi‑Fi Analyser claro: diagnóstico completo, dicas acionáveis e histórico, sem expor senhas de perfis e sem comandos destrutivos.

2. O que já existe hoje

  • já tem Op rede_wifi_analise — interface + perfis (sem senha) + drivers + gateway + dicas de sinal/banda
  • já tem rede_wifi_perfis, rede_wifi_drivers, rede_wifi_redes_proximas, rede_wifi_sinal_bars, rede_info_wifi_completo
  • já tem UI desktop em v10/rede-dashboard.js (botão “📡 Análise Wi‑Fi”)
  • já tem Mobile DECK com atalho para a mesma op
  • já tem Doc docs/REDE-DIAGNOSTICO.md
  • gap Relatório ainda é texto bruto do PowerShell — pouco “produto”
  • gap Sem mapa de canais / score visual / export JSON
  • gap Sem histórico estruturado só de Wi‑Fi (o painel tem histórico de saúde geral)

3. Escopo do produto (v1)

Entra na v1
  • Uma tela / seção “Wi‑Fi Analyser” no launcher (:7777)
  • Resumo visual: SSID, banda, canal, rádio, sinal %, Rx/Tx, gateway ms
  • Score simples (Bom / Médio / Crítico) com regras já usadas na op
  • Lista de redes próximas (canal + sinal) para ver interferência
  • Perfis salvos (nome apenas) e capacidade do adaptador
  • Botão “Rodar análise” → POST /run com rede_wifi_analise (+ ops auxiliares)
  • Exportar relatório .txt / .md
Fica fora da v1
  • Captura de handshake / chave / key=clear
  • Mudar canal do roteador automaticamente
  • App store separado (fica dentro do Mestre)
  • Mapa de calor físico da casa

4. Personas e fluxos

  1. Jean / uso diário: abrir Mestre → Rede → Análise Wi‑Fi → ler score + dicas em 30 s.
  2. Suporte remoto: rodar análise → copiar relatório → colar no chat.
  3. Mobile: no DECK, mesmo atalho; resultado legível em tela estreita.

6. Regras de segurança (não negociáveis)

  • Nunca mostrar ou pedir senha de Wi‑Fi / key=clear
  • Ops só na whitelist allowed-operations.json (Rede, não destrutivas)
  • Chamadas locais em 127.0.0.1 (não localhost)
  • Header de cliente esperado pelo launcher (X-Mestre-Client)

7. Métricas de sucesso

  • Análise completa em < 15 s no Nitro 5
  • Usuário entende “o que fazer agora” sem ler o dump do netsh
  • Zero regressão nas ops Rede existentes / testes de whitelist

8. Riscos e perguntas abertas

  • Saída do netsh muda com idioma do Windows (pt-BR vs en-US) — parsers frágeis
  • Launcher fora do ar → UI precisa do estado “offline” (já existe no painel)
  • Scan de redes próximas pode demorar / exigir rádio ligado

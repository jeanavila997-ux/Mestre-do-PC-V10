Status: Planejamento Estratégico

📊 1. Visão Geral do Projeto

O Mestre do PC V10/V11 é uma solução integrada de diagnóstico e manutenção Windows com foco em:
  • Backend MCP local (Node.js) que expõe ~33+ ferramentas de diagnóstico/manutenção
  • Launcher elevado (PowerShell 5.1 ou Node.js) que executa comandos whitelistados
  • Interface web SPA (HTML/JS) em `http://127.0.0.1:7777`
  • Integração IA via Ollama (local/cloud) com suporte a múltiplos modelos
  • Extensão de navegador (Manifest V3) para integração com browsers

💡 4. Análise & Recomendações para Multi-LLM

4.1 Situação Atual

✅ O que funciona bem:
  • Integração Ollama local/cloud já implementada e operacional
  • MCP protocol standard (v1.30.0 de @modelcontextprotocol/sdk)
  • Segurança robusta: whitelist, sanitização, prompt injection detection
  • Separação clara entre MCP (não elevado) e launcher (elevado)
  • Modelos locais com perfis pré-configurados (fast, balanced, agent, coding, reasoning)
❌ Limitações atuais:
  • Locked-in apenas em Ollama: não suporta Claude API, OpenAI, Gemini, etc. nativamente
  • Sem abstração de provider: todas as llamadas estão hard-coded para Ollama
  • Sem fallback automático entre providers
  • Sem suporte para streaming/agentic loops de outros LLMs
  • RAG/OpenAI Agents SDK ainda não implementados

4.2 Recomendações Estratégicas

Princípio #1: Provider Abstraction Layer

Criar camada de abstração que desacopla o MCP do provider específico de IA. 

mcp-server/
  providers/
    base-provider.js        // Interface abstrata
    ollama-provider.js      // Implementação Ollama
    claude-provider.js      // 🆕 Implementação Claude API
    openai-provider.js      // 🆕 Implementação OpenAI
    gemini-provider.js      // 🆕 Implementação Google Gemini
    provider-factory.js     // Factory pattern

Benefício: Trocar providers com uma linha de configuração, suportar fallback automático, e até usar múltiplos providers em paralelo.

Princípio #2: Configuration-Driven Provider Selection

Variável de ambiente única para escolher provider: 

# .env ou variáveis de ambiente

# Opção 1: Ollama (padrão, local)
AI_PROVIDER=ollama
OLLAMA_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen2.5-coder:1.5b

# Opção 2: Claude API
AI_PROVIDER=claude
ANTHROPIC_API_KEY=sk-ant-...
CLAUDE_MODEL=claude-opus-4-1-20250805

# Opção 3: OpenAI
AI_PROVIDER=openai
OPENAI_API_KEY=sk-proj-...
OPENAI_MODEL=gpt-4o

# Opção 4: Google Gemini
AI_PROVIDER=gemini
GOOGLE_API_KEY=AIzaSy...
GEMINI_MODEL=gemini-2.0-flash

# Opção 5: Fallback chain (tenta cada um até sucesso)
AI_PROVIDER=fallback
AI_PROVIDER_CHAIN=claude,openai,ollama
ANTHROPIC_API_KEY=sk-ant-...
OPENAI_API_KEY=sk-proj-...
OLLAMA_URL=http://127.0.0.1:11434

Benefício: Usuário escolhe o melhor provider para seu caso de uso sem alterar código. Fallback automático se um provider cair.

Princípio #3: Unified Tool Schema

Todos os providers implementam a mesma interface de ferramentas: 

interface AIProvider {
  // Consulta simples
  async query(prompt: string, context?: string): Promise<string>

  // Consulta com ferramentas (para agentes)
  async agentic_loop(
    system_prompt: string,
    user_message: string,
    available_tools: Tool[],
    max_iterations?: number
  ): Promise<AgenticLoopResult>

  // RAG: Query com contexto adicional
  async rag_query(
    query: string,
    documents: string[],
    instructions?: string
  ): Promise<string>

  // Chain-of-Thought
  async chain_of_thought(problem: string): Promise<ChainResult>

  // Comparar múltiplos modelos (novo)
  async compare_models(query: string, models?: string[]): Promise<ComparisonResult>

  // Health check
  async health(): Promise<HealthStatus>
}

Benefício: Tools do MCP não precisam saber qual LLM está sendo usado. Switching entre providers é transparente.

Princípio #4: Progressive Enhancement

Implementar features avançadas de forma gradual, sem quebrar compatibilidade:

Feature Ollama Claude OpenAI Gemini Status
Query Simples ✅ ✅ ✅ ✅ Presente
Tool Use / Agentic ✅ (parcial) ✅ (completo) ✅ (completo) ✅ (completo) Novo
Streaming ⚠️ (via curl) ✅ (nativo) ✅ (nativo) ✅ (nativo) Novo
Vision/Imagens ❌ ✅ ✅ ✅ Novo
Function Calling ❌ ✅ (Tool Use) ✅ ✅ Novo
Batch Processing ❌ ✅ (Batch API) ✅ ❌ Novo
Prompt Caching ❌ ✅ ❌ ❌ Novo

4.3 Arquitetura Proposta (Phase-based)

🔵 Phase 0: Abstraction Foundation (2-3 semanas)

Criar base sem quebrar compatibilidade Ollama existente.

  • Refatorar mcp-server/index.js para usar provider abstraction
  • Criar providers/base-provider.js (interface)
  • Implementar providers/ollama-provider.js (migração do código existente)
  • Criar providers/provider-factory.js
  • Testes: garantir que Ollama continua funcionando 100%

🟢 Phase 1: Claude API Support (2-3 semanas)

Suporte ao Claude como provider alternativo.

  • Implementar providers/claude-provider.js usando @anthropic-ai/sdk
  • Suporte a tool_use (function calling nativo do Claude)
  • Suporte a vision (análise de imagens)
  • Implementar fallback: Claude → Ollama se API_KEY não configurada
  • Docs: como configurar ANTHROPIC_API_KEY
  • Testes: teste de agentic loop com Claude

🟡 Phase 2: OpenAI & Gemini Support (2-3 semanas)

Suporte multi-provider via OpenAI SDK e Google Generative AI.

  • Implementar providers/openai-provider.js (OpenAI + Azure)
  • Implementar providers/gemini-provider.js (Google Gemini)
  • Suporte a batch processing (OpenAI Batch API para economia)
  • Suporte a streaming (todos os providers)
  • Config: seleção via AI_PROVIDER=openai, etc.

🟠 Phase 3: Advanced Features (3-4 semanas)

Recursos avançados que aproveitem capacidades de cada provider.

  • RAG Integration: Azure Search, Pinecone, ou local (em disco)
  • Streaming responses: UI web + WebSocket
  • Vision support: análise de logs em forma de imagens
  • Batch processing: economia de custos (OpenAI 50%, Claude Batch 50%)
  • Multi-model comparison: comparar respostas lado a lado
  • Prompt engineering studio: optimize prompts por provider

🔴 Phase 4: OpenAI Agents SDK & Microsoft Entra (4-5 semanas)

Integração de agentes avançados e SSO empresarial.

  • OpenAI Agents SDK: serviço Python separado para análise avançada
  • Microsoft Entra: SSO corporativo + autorização por grupos
  • Teams integration: notificações e alerts operacionais
  • Webhook support: eventos reativos via Graph change notifications

🎓 8. Benefícios Esperados

Para Desenvolvedores

  • Code Reusability: Plugin pattern permite adicionar novos providers em ~200 linhas
  • Testing: Cada provider testado independentemente + testes de integração
  • Fallback: Configuração automática de fallback reduz downtime

Para Usuários

  • Flexibilidade: Escolher melhor LLM para seu caso (local, barato, poderoso, etc.)
  • Economia: Batch processing (OpenAI 50%), Prompt Caching (Claude 90%)
  • Privacidade: Opção de rodar 100% local com Ollama
  • Confiabilidade: Fallback automático se um provider cair

Para Arquitetura

  • Future-proof: Fácil adicionar novos providers (Anthropic Cloud, xAI Grok, etc.)
  • Decoupling: MCP não precisa saber qual LLM está sendo usado
  • Modularity: RAG, streaming, vision são features ortogonais

✅ 9. Conclusão & Próximos Passos

O Mestre do PC V10/V11 possui uma base sólida e segura para integração MCP. Com abstração de providers, é possível suportar múltiplos LLMs mantendo 100% compatibilidade com Ollama existente e preparando o caminho para recursos empresariais (Entra ID, Teams, RAG, Agents SDK).

🚀 Recomendação Estratégica

  1. Começar imediatamente com Phase 0 (abstração de providers) — é o fundamento necessário para tudo mais
  2. Priorizar Claude API na Phase 1 — melhor custo-benefício para experiência de desenvolvedor
  3. Considerar RAG (Phase 3) — agregador de valor para diagnósticos mais contextualizados
  4. Deixar Entra/Teams para Phase 4 — depende de caso de uso empresarial
  5. Integrar com awesome-copilot-agents — criar Agent Skill portável para PC Diagnostics
⏱️ Estimativa Total: 18-24 semanas (4-6 meses) para todas as 4 fases, ou 6-9 semanas (1.5-2 meses) para Phase 0-1 (MVP multi-LLM).

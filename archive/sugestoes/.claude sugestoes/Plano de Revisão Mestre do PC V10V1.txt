O que falta é essa memória sobreviver a "limpar dados do navegador" e (mais adiante) ser compartilhada entre dispositivos/usuários via Supabase.O usuário confirmou que quer remover a barreira da whitelist para permitir execução livre — ciente de que isso desativa uma proteção central do projeto. Confirmou também que quer, num momento futuro, usar um projeto Supabase já existente para cadastro de clientes e cobrança por assinatura (MCP grátis com poucos comandos; chat + execução automática só para assinantes). Ela deve ser implementada como um modo explícito, opt-in e reversível (não uma reescrita silenciosa das funções de segurança), para que o usuário saiba exatamente quando está exposto a risco de comando destrutivo/acidental, e para deixar o caminho aberto para o gate por assinatura do roadmap Supabase (ligar/desligar por usuário, não só globalmente).---Parte A — Modo de Execução Livre (agora)Objetivo: o chat pode rodar qualquer comando PowerShell, sem checar `allowed-operations.json` e sem popup de confirmação — mas isso é um modo que o usuário liga explicitamente, com auditoria total, não uma remoção da whitelist para todo mundo.`v10/launcher.js` — nova rota `POST /run-free` (nome sugerido), paralela a `/run`:Aceita `{ cmd: string }` diretamente (sem `operationId`), chama `runPowerShell(cmd, { id: "livre", destructive: true })` (reaproveita a função existente em `launcher.js:331`).Autorização: mesma checagem de `X-Mestre-Client: v10-web` + origem local já usada em `/run` — não abrir para rede externa.Gate por flag: só responde se um modo estiver ativo (ver item 3).

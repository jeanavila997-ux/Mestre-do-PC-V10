SUGESTÃO DE MELHORIAS — ANÁLISE DE DEPENDÊNCIAS
Projeto: Mestre-do-PC-V10
Data: 24/08/2026

OBJETIVO

Registrar melhorias recomendadas para a arquitetura de dependências do projeto sem tratar o estado atual como uma correção emergencial de código.

CONCLUSÃO ATUAL

O estado das dependências está, de modo geral, enxuto e organizado. Não há evidência suficiente de uma falha funcional que exija alteração imediata de código.

As principais oportunidades estão em:
1. Isolar dependências opcionais.
2. Formalizar a análise de vulnerabilidades transitivas.
3. Automatizar auditoria de dependências no CI.
4. Manter lockfiles e overrides sob controle.
5. Separar futuras atualizações arquiteturais de correções emergenciais.

1. MCP-SERVER — OVERRIDES

Estado atual:
- Dependência direta principal: @modelcontextprotocol/sdk.
- Existem overrides para:
  - hono
  - @hono/node-server
  - fast-uri
  - path-to-regexp
  - qs
  - body-parser

Avaliação:
- A utilização de overrides é uma estratégia válida para controlar dependências transitivas e mitigar vulnerabilidades conhecidas.
- Os overrides devem ser tratados como uma política de segurança/manutenção e não como solução permanente sem revisão.

Melhorias recomendadas:
- Documentar o motivo de cada override.
- Registrar a versão afetada, a versão aplicada e a vulnerabilidade relacionada.
- Revisar os overrides periodicamente.
- Confirmar compatibilidade sempre que uma versão for alterada.
- Evitar overrides sem justificativa técnica registrada.

Modelo sugerido de registro:

Dependency Risk
- Package:
- Vulnerability:
- Severity:
- Affected Version:
- Applied Version:
- Reachability:
- Exploitability:
- Mitigation:
- Reason for Override:
- Review Date:

2. @HONO/NODE-SERVER — ANÁLISE DE RISCO REAL

Estado atual:
- O README registra uma vulnerabilidade moderada relacionada ao @hono/node-server.
- O servidor utiliza stdio em vez da rota HTTP potencialmente afetada.

Avaliação:
- Isso deve ser tratado como análise de risco baseada em reachability, e não simplesmente como erro gerado pelo npm audit.
- A presença do pacote na árvore de dependências não implica, por si só, exploração do caminho vulnerável.

Melhorias recomendadas:
- Documentar formalmente a justificativa.
- Identificar exatamente quais componentes usam HTTP e quais utilizam stdio.
- Verificar se algum caminho HTTP pode ser habilitado futuramente.
- Definir uma data de revisão dessa exceção.

Resultado esperado:
- Redução de falsos positivos operacionais.
- Decisões de segurança rastreáveis.
- Menor risco de remover uma dependência necessária sem necessidade.

3. V10 — MYSQL2

Estado atual:
- v10 possui mysql2 como dependência direta.
- O arquivo v10/chat-integrado/mysql-sync.js importa mysql2/promise.js.
- Existe fallback para ausência da dependência ou falha de conexão.

Avaliação:
- Isso sugere que MySQL pode ser uma integração complementar.
- A dependência não deve ser removida antes de confirmar sua importância funcional.

Melhoria prioritária:
- Determinar se mysql2 é:
  a) obrigatório para o funcionamento principal;
  b) opcional;
  c) usado apenas em uma funcionalidade específica;
  d) legado.

Caso seja opcional:
- Isolar a integração em módulo/feature opcional.
- Evitar carregar mysql2 no caminho de inicialização do núcleo.
- Considerar carregamento sob demanda.
- Avaliar uma feature flag para ativação.
- Manter mensagens claras quando a integração não estiver disponível.

Arquitetura desejável:

Core V10
|
+-- Diagnóstico
+-- Manutenção
+-- PowerShell
+-- MCP
|
+-- Integrações opcionais
    |
    +-- MySQL
    +-- Outros conectores futuros

4. BROWSER-EXTENSION

Estado atual:
- Não possui dependências diretas.

Avaliação:
- É uma situação positiva.
- Reduz superfície de ataque, manutenção e risco de supply chain.

Melhorias recomendadas:
- Manter o número de dependências próximo de zero enquanto tecnicamente viável.
- Evitar adicionar bibliotecas apenas por conveniência.
- Preferir APIs nativas do navegador quando a complexidade justificar.

5. CI — SEGURANÇA DE DEPENDÊNCIAS

Objetivo:
Automatizar a validação sem permitir atualizações destrutivas ou inesperadas.

Pipeline recomendado:

npm ci
npm audit --omit=dev
npm outdated

Além disso:
- Validar lockfiles.
- Garantir que package-lock.json permaneça versionado.
- Revisar mudanças no dependency tree em pull requests.
- Registrar exceções de vulnerabilidade quando uma atualização imediata não for viável.

Importante:
- Não executar npm audit fix --force automaticamente no CI.
- Atualizações potencialmente incompatíveis devem passar por revisão.

6. POLÍTICA DE LOCKFILES

Recomendações:
- Manter package-lock.json versionado.
- Usar npm ci em ambientes de CI/deploy.
- Evitar alterações manuais no lockfile.
- Atualizar lockfiles por meio do npm.
- Revisar diferenças do dependency tree quando houver atualização relevante.

Objetivo:
- Builds reproduzíveis.
- Menor divergência entre desenvolvimento, CI e produção.
- Melhor rastreabilidade.

7. GOVERNANÇA DOS OVERRIDES

Criar uma regra interna:

Cada override deve possuir:
- Justificativa.
- Vulnerabilidade ou incompatibilidade associada.
- Versão mínima/segura definida.
- Data da última revisão.
- Responsável pela validação.

Evitar:
- Overrides sem documentação.
- Pinagem indefinida sem acompanhamento.
- Dependências transitivas forçadas sem testes de compatibilidade.

8. SEPARAÇÃO ENTRE RUNTIME E TOOLING

Verificar a separação entre:
- Dependências de produção.
- Dependências de desenvolvimento.
- Ferramentas de build.
- Testes.
- Integrações opcionais.

Objetivo:
- Reduzir superfície de produção.
- Facilitar auditoria.
- Melhorar previsibilidade do pacote final.

10. SDK DO MCP — BACKLOG FUTURO

A evolução do SDK MCP deve ser tratada separadamente desta análise.

Recomendação:
- Criar uma task específica para avaliar a evolução/migração do SDK.
- Identificar breaking changes.
- Mapear APIs atualmente utilizadas.
- Criar testes de compatibilidade antes da migração.
- Não misturar atualização arquitetural com correção de vulnerabilidade sem necessidade.

11. ROTINA DE REVISÃO

Periodicidade sugerida:
- Auditoria automática: cada pipeline relevante.
- Revisão de dependências: mensal.
- Revisão de overrides: mensal ou quando houver advisory relevante.
- Revisão arquitetural do MCP SDK: trimestral.
- Revisão extraordinária: imediatamente após vulnerabilidade crítica relevante.

P0 — Imediato
- Documentar o racional do @hono/node-server.
- Confirmar o papel funcional do mysql2.
- Garantir package-lock.json versionado.
- Adicionar npm ci e npm audit ao CI.

P1 — Curto prazo
- Criar inventário dos overrides.
- Criar registro de riscos de dependências.
- Separar claramente runtime, tooling e integrações opcionais.
- Revisar caminhos de inicialização que importam mysql2.

P2 — Médio prazo
- Isolar completamente MySQL como feature opcional, caso confirmado.
- Criar política formal de dependências.
- Avaliar uso de npm workspaces.

P3 — Backlog estratégico
- Avaliar migração/evolução do MCP SDK.
- Evoluir governança de supply chain.
- Integrar ferramentas adicionais de análise de composição de software, se necessário.

13. CRITÉRIOS DE ACEITE

A melhoria pode ser considerada concluída quando:

[ ] O papel do mysql2 estiver documentado e classificado como obrigatório ou opcional.
[ ] O risco associado ao @hono/node-server estiver documentado com justificativa de reachability.
[ ] Os overrides possuírem justificativa e versão-alvo registradas.
[ ] O CI executar instalação reprodutível com npm ci.
[ ] O CI executar auditoria de dependências.
[ ] Os lockfiles estiverem versionados.
[ ] Dependências opcionais estiverem separadas do núcleo quando aplicável.
[ ] Alterações de dependências puderem ser rastreadas em pull requests.
[ ] Uma task separada existir para avaliação futura do SDK MCP.

CONCLUSÃO FINAL

O projeto está em uma direção saudável em relação à superfície de dependências.

A prioridade não deve ser remover dependências indiscriminadamente, mas aumentar o controle sobre elas.

A melhoria de maior valor é transformar o estado atual em uma política contínua:

- dependências mínimas;
- integrações opcionais isoladas;
- overrides documentados;
- vulnerabilidades analisadas por reachability;
- lockfiles reproduzíveis;
- auditoria automatizada;
- atualizações arquiteturais separadas de correções emergenciais.

Essa abordagem reduz risco técnico e de supply chain sem criar mudanças desnecessárias no núcleo do Mestre-do-PC-V10.
